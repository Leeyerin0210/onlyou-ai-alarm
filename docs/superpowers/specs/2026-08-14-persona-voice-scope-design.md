# 페르소나·음성 범위 재설계 (2026-08-14)

지금 페르소나 시스템은 Character.ai에 가깝다. 유저가 40,000자짜리 시스템 프롬프트를
자유 서술하고, 목소리도 자유 프롬프트로 생성하며, 결과물을 공개 상점에 올려 다른
유저에게 노출한다. 이 구조는 캐릭터 챗 유저층을 부르는데, 그 층의 핵심 수요(19금)를
우리는 v1에서 지원하지 않는다. 결과적으로 이탈할 유저를 획득 비용 들여 데려오면서,
그들이 남기는 리뷰와 상점 노출로 정작 남을 유저를 쫓아내는 구조다.

동시에 자유 입력은 검열과 무관한 비용도 발생시킨다 — 서버리스 GPU 호출 폭증,
유저 수에 비례하는 음성 파일 저장, 품질 복불복, 임의 오디오 업로드 구멍.

이 문서는 페르소나를 **"목적"에서 "인터페이스"로** 되돌리는 설계를 정한다. 제품은
캐릭터 앱이 아니라 대중용 AI 비서이며, 페르소나는 그 비서를 견딜 만하게 만드는
껍데기다. 음성 호출(핫워드) 조사 결과도 함께 기록한다.

## 결정 요약

| 항목 | 결정 |
|---|---|
| 제품 방향 | 대중용 AI 비서. 타겟 넓게, 주력 20~40대 |
| 페르소나 프롬프트 | 자유 서술 **제거**. 우리가 만든 프리셋 8~12개 |
| 연애 감정 | 유저가 느끼는 것은 **부정하지 않는다**. 다만 상품화·게임화하지 않는다 |
| 성별 있는 캐릭터 | **허용**(오지랖 아저씨 등). 성별 태그도 UI에 표시 |
| 상점 1차 탐색축 | 역할·상황. 성별로 브라우징하는 화면은 만들지 않음 |
| 목소리 | 프리셋 10개. 페르소나와 **분리**해 조합 |
| 목소리 매칭 | 성별 태그로 **소프트 유도**(맞는 것 우선, 나머지는 접기) |
| 유저 커스터마이징 | 프리셋 조합 + 이름 + 호칭. 톤·속도 슬라이더는 **제거** |
| 공개 공유 | v1에서 **제거**. 유저 생성물은 비공개 전용 |
| 모더레이션 | 불필요 — UGC가 아니게 되므로 의무 자체가 소멸 |
| 캐릭터 일러스트 | v1에서 제거. 얼굴 없는 시각 정체성(색·형태) |
| 19금 옵션 | v1 범위 밖. 근거는 정책 불가가 아니라 **리스크 대비 이득** |
| 음성 수위 | 텍스트보다 **항상 더 엄격**. 19금을 열더라도 음성은 열지 않는다 |
| 음성 호출 | v1은 위젯 + 퀵설정 타일. 핫워드·어시스턴트 등록은 v2 옵트인 |

## 배경: 지금 구조의 문제

### 자유 입력 4종

| 필드 | 현재 | 문제 |
|---|---|---|
| `prompt` | 40,000자 자유 서술 | 우리가 안 쓴 시스템 프롬프트가 LLM에 그대로 들어가고, 그 출력이 TTS로 나감 |
| `voice_prompt` | 1,000자 자유 서술 | 텍스트 검열을 우회하는 유일한 통로(숨소리·속삭임 등 비언어 발화) |
| `image_url` | 임의 URL | 아무 이미지나 상점에 노출 가능 |
| `save_reference` API | 임의 오디오 바이트 | 연예인·지인 목소리를 올려 클로닝 가능 (음성권 문제) |

### 모더레이션 부재

`routers/personas.py`, `core/`, `services/` 전체에 콘텐츠 검열 코드가 없다.
`tests/test_abuse_guards.py`의 방어는 전부 크기 제한·레이트리밋·`usage_count`
위조 방지뿐이다. `upsert_persona`는 소유권만 확인하고 내용은 읽지 않으며,
`is_private=false`면 그대로 전체 상점에 노출된다.

구글 플레이 UGC 정책은 유저 생성 콘텐츠를 공유하는 앱에 신고 기능과 검열 수단을
요구한다. 현 구조를 유지하려면 이 의무가 발생한다.

### 검열과 무관한 비용

- **GPU** — `tts-server/modal_app.py`는 Modal 서버리스 L4, `scaledown_window=5분`.
  컨테이너 가동 시간만큼 과금된다. 그런데 `PersonaEditScreen.kt:318`은
  `"마음에 들 때까지 다시 생성할 수 있어요"` — 페르소나 하나당 GPU 추론이 수~수십 회
  돈다. 유저가 대기 중이라 우선순위를 낮출 수도 없어, 알람 사전생성(`PreGenWorker`)과
  같은 GPU를 놓고 경쟁한다.
- **스토리지** — 마스터 wav/json이 `persona_id`별로 GCS에 쌓인다. 유저 수 × 페르소나 수.
- **품질** — 자유 생성 결과는 복불복이다. 채팅은 다시 들으면 되지만 **알람은 한 번
  울리고 끝**이다. 유저가 "목소리가 이상하다"고 해도 우리가 만든 게 아니라 재현도
  대응도 불가능하다.

## 제품 방향

**대중용 AI 비서.** 캐릭터 컴패니언 앱과의 갈림길에서 전자를 택한다.

19금을 v1에서 지원하지 않기로 한 이상, 그 제약 아래에서 캐릭터 앱은 리텐션 천장이
구조적으로 낮다. 반면 알람·일정이라는 실용 축은 캐릭터 앱들이 갖고 있지 않은 땅이다.

`GEMINI.md` 5번의 "초개인화된 유대감"은 이 방향에서도 온전히 지켜진다. 유대는
서사와 외모가 아니라 **나를 기억한다는 사실**에서 오고, 그건 RAG가 하는 일이다.

## 페르소나 설계

### 페르소나는 역할이지 캐릭터가 아니다

상점에 나열되는 것은 캐릭터 목록이 아니라 **역할 목록**이다. 성별은 역할에 딸려오는
속성이지 탐색 축이 아니다.

- 1차 탐색축: 역할·상황 (아침에 깨워주는 / 일정 챙겨주는 / 편하게 수다떠는 …)
- 성별로 브라우징하는 화면은 만들지 않는다.

### 연애 감정에 대한 입장

세 가지를 구분한다.

| | 내용 | 우리 결정 |
|---|---|---|
| 유저가 연애 감정을 느끼는 것 | 좋은 비서를 만들면 일부는 그렇게 느낀다 | **우리 소관이 아니다.** 막지 않는다 |
| 연애 관계를 상품으로 파는 것 | 상점의 "여자친구" 프리셋 | 하지 않는다 |
| 연애를 게임화하는 것 | 애정도, 관계 진전, 질투 | 하지 않는다 |

매일 나를 기억하고 깨워주는 존재에게 애착이 생기는 것은 병리가 아니라 애착이
작동하는 방식이다. 그것을 부정하는 제품은 자기 가치를 부정하는 것이다. 따라서:

- **AI는 먼저 연애 프레임을 꺼내지 않는다.** 유저가 애정을 표현하면 차갑게 거부하지도
  않는다.
- 이름 자유, 호칭 자유, 다정한 말투 프리셋이 있고, 유저가 그것을 어떻게 쓰든 막지 않는다.
- **게임화 장치는 만들지 않는다.** 19금 수요를 직접 끌어오는 것은 다정한 말투가 아니라
  관계를 진전시키는 게임 루프다. "다음 단계에 뭐가 있을까"가 기대를 만들고 그 기대의
  끝이 19금이다. 루프가 없으면 수요도 생기지 않는다.

부가 규칙:
- **연령을 특정하지 않는다.** 성격은 살리되 미성년 설정은 붙이지 않는다
  ("츤데레 여고생" → "툴툴대는 후배"). AI 컴패니언 + 미성년 조합은 심사에서 민감하다.
- **서브컬쳐 어휘 대신 대중 어휘로 라벨링한다.** "츤데레" → "겉으로는 툴툴대는데
  은근히 챙겨주는". 성격도 프롬프트도 같고 라벨만 다르다. 아는 사람은 알아보고,
  모르는 사람은 재밌는 성격이라고 읽는다.
- 스토어 스크린샷·온보딩 기본값에는 대중형만 노출한다. 앱 내부 상점에 캐릭터성 강한
  페르소나가 있는 것과, 스토어 첫인상이 그것으로 결정되는 것은 다른 문제다.

### 프리셋 축

성격 프리셋은 무작위로 만들지 않고 축을 세워 서로 최대한 멀게 만든다.
축 없이 30개를 만들면 유저는 그것을 5개로 느낀다.

- 존댓말 / 반말
- 간결 / 수다스러움
- 다정 / 무뚝뚝
- 채근 / 응원

개수는 **8~12개**. 20~30개는 선택 피로를 낳고(실제로는 상위 3~5개만 쓰인다),
모델 교체·공통 지침 변경 때마다 전부 재검증해야 하는 영구 부채가 된다.

### 프리셋 정의는 어디에 두나

프리셋 본문(성격 서술 · 말투 지침)은 **서버 코드의 상수**로 둔다. DB가 아니다.
프리셋은 프롬프트 엔지니어링 산출물이라 코드 리뷰·버전 관리 대상이어야 하고,
모델을 바꿀 때 전체를 함께 재검증해야 하기 때문이다.

`personas.preset_key`는 그 상수를 가리키는 참조값이며, 서버가 요청 시
`preset_key` + `name` + `user_call_sign`을 조합해 최종 시스템 프롬프트를 만든다.

**합성 결과는 저장하지 않는다.** `personas.prompt`에 캐시하는 안은 버린다 — 프리셋
문구를 고치는 순간 저장된 행 전부가 낡은 값이 되어 재합성 배치가 필요해지고, 프리셋은
코드 상수라 읽는 비용이 0인데 캐시를 두면 무효화 문제만 새로 생긴다. `prompt` 컬럼은
읽지도 쓰지도 않는 상태가 되고, 마이그레이션에서 제거된다.

남는 것은 "요청 시점에 프리셋 본문 + 이름·호칭 블록을 이어붙이는 문자열 결합" 뿐이며,
이것을 별도 합성 계층으로 만들지 않는다.

## 목소리 설계

### 페르소나와 분리한다

현재는 `personas` 테이블에 `voice_prompt`가 있고 레퍼런스 wav도 `persona_id`로
저장되어, 페르소나 하나 = 목소리 하나로 결박되어 있다. 이를 분리한다.

| | 우리가 만드는 것 | 유저 체감 |
|---|---|---|
| 성격 프리셋 | 8~12개 | |
| 목소리 프리셋 | 10개 | |
| 이름 · 호칭 | 자유 | |
| **결과** | **자산 ~20개** | **조합 80~120가지 + 이름 무한** |

자산은 덧셈, 체감은 곱셈이다.

### 프리셋 10개는 격자로 만든다

성별 2 × 연령대 2 × 분위기 2~3 정도로 서로 구분되게 만든다. 한 번 들어 구분되지
않으면 10개가 아니라 3개다.

목소리 프리셋에는 성별을 표기한다. 유저는 실제로 "남자 목소리 / 여자 목소리"로 찾는다.

### 성별 태그로 소프트 유도

페르소나에 성별 태그를 붙인다. 둘 다 어울리면 둘 다, 하나만 어울리면 하나만.

- 태그가 `[남성, 여성]` → 목소리 전체 노출
- 태그가 `[남성]` → 남자 목소리 우선 노출, 나머지는 "다른 목소리도 보기"로 접기

**하드 필터가 아니라 소프트 유도**다. 기본 경로는 항상 잘 맞고, 벗어나는 유저는
자기가 원해서 간 것이라 어색해도 납득한다.

페르소나별로 **추천 목소리를 하나씩 지정**해 기본 선택값으로 쓴다.

> **예외 규칙 (크리에이터 파트너십 도입 시)** — 파트너가 제공한 목소리는
> 페르소나와 **묶음으로 고정**한다(하드 락). 조합 자유를 허용하면 그 목소리의
> 주인이 하지 않을 말을 그 목소리로 하게 되며, 파트너가 허용할 수 없다.
> 잠금 플래그 하나를 `personas`에 추가하면 된다. 아래 "향후 확장 가능성" 참조.

### 자유 생성은 내부 도구로 남긴다

`synthesize_design`은 삭제하지 않는다. 우리가 프리셋을 만들 때 쓰는 도구로 남기고,
앱 UI에서만 제거한다. `save_master_wav` / `load_reference` / `synthesize_clone`
파이프라인은 그대로 쓴다 — **"생성" 단계를 유저에게서 우리에게로 옮기는 것뿐**이라
버리는 코드가 거의 없다.

### 프리셋 전환의 부수 효과

- 유저 트래픽에서 VoiceDesign 호출이 0이 된다. 알람 사전생성과의 GPU 경쟁 해소.
- 레퍼런스 파일이 10개로 고정. 스토리지 비용 예측 가능, 개인정보 파기 대상도 소멸.
- 10개를 직접 듣고 검수하므로 이상한 음성이 나갈 수 없다.
- `/voice/save_reference` 엔드포인트를 닫을 수 있다 (임의 오디오 업로드 구멍 차단).

### 프리셋 제작 시 주의

목소리를 매력 없게 만들 필요는 없다. 심의는 기본적으로 내용을 보며, 목소리 톤 자체가
문제된 사례는 확인되지 않는다. 피해야 할 것은 매력이 아니라 **비언어 발화**다 —
`instruct`에 "숨소리 섞인", "귓가에 속삭이는" 같은 표현을 넣지 않는다.

## 음성은 텍스트보다 항상 엄격하게

19금 옵션을 나중에 열더라도 **음성은 열지 않는다.** 이유는 넷이고 마지막이 결정적이다.

1. **유포력** — 음성은 독립 파일로 떨어져 나간다. 클립 하나가 퍼지면 "이 앱이 이런 걸
   만든다"가 즉시 증명된다.
2. **심의 관행** — 같은 내용이라도 시청각 요소가 붙으면 등급이 올라가는 것이 일반적이다.
   (한국 심의 실무 사례까지 확인하지는 않았다.)
3. **생성 주체** — 텍스트는 LLM 출력이지만 음성은 우리 Modal 인스턴스가 합성한다.
   로그·캐시에 남으면 보관 리스크가 된다.
4. **통제 지점이 없다** — 텍스트 19금은 필터로 등급을 조절할 수 있다. 음성의 위험은
   **비언어 발화**에 있고, 그것은 텍스트에 없으므로 텍스트 필터가 100% 놓친다.
   조절 손잡이가 우리 손이 아니라 모델 안에 있다.

**정책: 19금 모드를 열게 되면 그 대화에서는 TTS를 비활성화한다.** 어정쩡하게 읽어주다
마는 것보다 "이 대화는 음성 지원이 안 됩니다"가 일관된다.

이 비용은 사실상 0이다. 우리 제품에서 음성의 주 용도는 알람이고, **알람 음성이 19금일
이유가 없다.** 19금이 일어난다면 채팅이고 채팅은 원래 텍스트가 주력이다.

## 19금 옵션을 v1에 넣지 않는 이유

경쟁 앱(크랙 등)이 성인 옵션을 두고도 낮은 연령등급으로 운영되는 사례가 있다.
이것이 가능한 이유와, 그럼에도 우리가 v1에서 하지 않는 이유를 기록한다.

**가능한 이유** — 플레이 연령등급은 IARC 설문에 개발자가 **자기신고**한 값이다.
구글이 사전에 앱을 뜯어보고 매기지 않는다. 따라서 성인 기능이 있는데 낮게 신고하는 것이
물리적으로 가능하다.

**그럼에도 위험한 이유** — 등급 오신고는 삭제·정지 대상이며, 제재 범위는 설문 재작성
요구부터 앱 삭제와 개발자 계정 정지까지다. 유저가 스토어에서 등급을 신고할 수 있고,
구글은 심사 파이프라인에 생성형 AI를 넣어 콘텐츠 불일치를 탐지한다. 기능 변경으로
설문 답이 달라지면 재제출 의무가 있다.

즉 **가능한 것은 맞지만 그것은 허가가 아니라 지연이다.** 그리고 리스크가 비대칭이다 —
작을 때는 아무도 보지 않고, 커지면 본다. 제재가 오는 시점이 성공한 뒤라 되돌리는 비용이
가장 클 때 온다.

**우리와 상황이 다른 점**
- 대응 여력: 크랙은 투자받은 회사(뤼튼)의 제품으로 법무·정책 대응 인력이 있다.
  개인 개발 규모에서 계정 정지는 앱 전체의 사망이다.
- 얻는 것의 크기: 캐릭터 챗이 본체인 서비스에게 성인 옵션은 **핵심 리텐션 장치**다.
  알람이 본체인 우리에게는 부가 기능이다. **같은 리스크를 지고 훨씬 작은 것을 산다.**
- 후발주자가 더 눈에 띈다. 먼저 자리 잡은 앱에는 관성이 있다.

**결론** — v1 범위 밖. 근거는 "정책상 불가능"이 아니라 "리스크 대비 이득이 맞지 않음"이다.
앱이 자리를 잡고 대응 여력이 생기면 별도 앱 또는 별도 트랙으로 **재검토 가능한 판단**이다.
다만 그때도 음성은 열지 않는다.

> **단, 크리에이터 파트너십 노선을 타면 이 재검토 여지가 사라진다.** 실존 인물의
> 목소리로 19금 대화가 이뤄지는 것은 계약 위반이자 그 사람의 명예·커리어 훼손이며,
> 플랫폼 책임이 우리에게 온다. 두 노선은 상호배타적이므로 **어느 쪽을 택할지가
> 19금 재검토보다 앞선 결정**이다. 아래 "향후 확장 가능성" 참조.

### 톤·속도 슬라이더를 제거하는 이유

애초에 **연결된 적이 없는 배관**이다. 구현을 확인한 결과:

- `PersonaEditScreen.kt`에 톤·속도 슬라이더 UI가 없다. 그 파일의 유일한 `Slider`는
  오디오 재생 진행바다.
- `voice_service.py`의 `synthesize_clone`은 `text` + 레퍼런스 오디오만 TTS 서버로
  보낸다. 톤·속도는 전달되지 않는다.
- 앱에 `PlaybackParameters` / `setSpeed` 호출도 없다.

그럼에도 `voiceTone` · `voiceSpeed`는 **DB 컬럼 · `PersonaDto` · `PersonaEntity` ·
`Persona` 도메인 모델 · `PersonaIn`** 5겹에 존재한다. 값을 받아 저장하고 돌려주기만
하는 순수 배관이다.

목소리를 프리셋화하면 톤은 프리셋이 결정한다. 유저에게 손잡이를 다시 주면 "10개를
직접 듣고 검수하므로 이상한 음성이 나갈 수 없다"는 근거가 약해진다.

**컬럼 DROP은 지금 하지 않는다.** 앱·DTO·API 경로에서만 걷어내고, 컬럼 제거는
`voice_prompt` · `image_url`과 함께 마이그레이션 단위에서 처리한다. 지금 지우면
구버전 앱이 붙어 있는 동안 깨진다.

**공통 지침에 "자기 성별을 언급하지 말 것"을 넣는다.** 유저가 이름을 "미야"로 짓고
남자 목소리를 골랐는데 AI가 스스로를 "언니"라고 부르면 몰입이 깨진다.

## UGC 판정 기준

무엇이 규제 대상인지 판단하는 축은 둘이다.

1. **전달되는가** — 혼자 보는 것은 설정이고, 남에게 보이면 유통이다.
2. **표현 공간이 우리 손 안인가** — 우리가 정한 유한한 선택지면 설정, 임의 생성이
   가능하면 콘텐츠다.

| 필드 | 성격 | 판정 |
|---|---|---|
| `primary_hex`, `secondary_hex` | 색상 — 표현력 없음 | 설정 |
| 프리셋 선택 | 우리가 쓴 것 중 고르기 | 설정 |
| `name`, `description` | 자유 텍스트(짧음) | 경계선 |
| `prompt`, `voice_prompt` | 자유 텍스트(김) | 콘텐츠 |
| `image_url` | 임의 URL | 콘텐츠 |

v1 설계에서는 자유 텍스트가 `name`·`user_call_sign`만 남고 **공개 공유가 없으므로
UGC 앱이 아니게 된다.** 신고 기능·검열 파이프라인 의무가 통째로 사라진다.

단, **UGC 정책(유통)과 LLM 출력 안전(생성)은 별개 문제**다. 자유 프롬프트를 비공개로만
쓰더라도 그 출력은 우리 서비스의 출력이다. 그래서 비공개라도 자유 프롬프트는 제거한다.

## 스키마 변경 (`backend/core/rdb.py`)

```sql
-- 페르소나: 목소리 종속 제거, 태그·추천 목소리 추가
ALTER TABLE personas ADD COLUMN IF NOT EXISTS tags TEXT[] NOT NULL DEFAULT '{}';
ALTER TABLE personas ADD COLUMN IF NOT EXISTS default_voice_id TEXT;
ALTER TABLE personas ADD COLUMN IF NOT EXISTS preset_key TEXT;

-- 목소리 프리셋 카탈로그
CREATE TABLE IF NOT EXISTS voices (

```

`tags`는 성별 전용 컬럼 대신 배열로 잡는다. 나중에 `#존댓말` `#간결` `#아침형` 같은
축을 같은 구조로 붙일 수 있고, `ShopScreen.kt:119`의 카테고리 필터도 이 태그를 쓰면
상점 필터와 목소리 매칭이 하나의 메커니즘으로 돌아간다. 비용은 `TEXT` 대신 `TEXT[]`
정도의 차이다.

레퍼런스 wav 저장 키를 `persona_id`에서 `voice_id`로 바꾼다
(`voice_service.py`의 `_local_paths`, `save_master_wav`, `load_reference`).

## API 변경

| 엔드포인트 | 변경 |
|---|---|
| `PUT /personas/{id}` | `prompt`·`voice_prompt`·`image_url`·`voiceTone`·`voiceSpeed` 수용 중단. `preset_key`+`name`+`user_call_sign`+색상만 받는다 |
| `POST /chat` | `system_prompt` 수용 중단. 서버가 유저의 선택 페르소나에서 조립 |
| `POST /alarm_script` | `persona_prompt`·`persona_name`·`user_call_sign` 수용 중단. 같은 경로로 조립 |
| `GET /presets` | **신규** — 성격 프리셋 목록(라벨·설명·태그). 프롬프트 본문은 내보내지 않는다 |
| `POST /voice/save_reference/{id}` | **제거** (임의 오디오 업로드 구멍) |
| `GET /voices` | **신규** — 목소리 프리셋 목록 |

| `GET /personas` | `is_private` 공개 목록 로직 정리 — 공식 카탈로그 + 본인 것 |
| `DELETE /personas/{id}` | 레퍼런스 정리 호출 추가 (아래 참조) |

`MAX_SYSTEM_PROMPT_LEN = 40_000`은 클라이언트 입력 경로에서 불필요해진다
(서버가 조립한 프롬프트에는 여전히 적용).

### 프롬프트를 지금 누가 만드는가

구현을 확인한 결과, **시스템 프롬프트는 앱이 통째로 조립한다.**
`ChatRepositoryImpl.kt`의 `buildSystemPrompt()`가 페르소나 프롬프트 + 유저 호칭 +
누적 유저 노트 + 공통 지침 + 탈옥 대응 지침을 합쳐 `POST /chat`의 `system_prompt`로
보낸다. 알람도 `AlarmScriptRequest.persona_prompt`로 같은 값을 보낸다.

따라서 `PUT /personas`에서 자유 프롬프트를 막는 것만으로는 **LLM에 들어가는 프롬프트를
우리가 통제하게 되지 않는다.** 이 스펙이 지적한 위험("우리가 안 쓴 시스템 프롬프트가
LLM에 그대로 들어가고, 그 출력이 TTS로 나감")의 실제 통로는 `PUT /personas`가 아니라
`POST /chat`이다. 그래서 서버 조립은 `/chat` · `/alarm_script`까지 함께 옮긴다.

부수 효과로 **공통 지침·탈옥 대응 문구를 앱 업데이트 없이 배포**할 수 있게 된다.
지금은 그것들이 앱 바이너리 안에 있어 스토어 심사를 거쳐야 바뀐다.

유저 노트는 현재 기기 Room DB에만 있으므로, 요청 바디에 별도 필드로 계속 받는다 —
페르소나 프롬프트와 달리 유저 노트는 유저 본인의 데이터이지 우리가 쓴 지침이 아니다.

## 별도 발견: 레퍼런스 파일 누수

`routers/personas.py:70`의 `delete_persona`가 DB 행만 삭제하고
`voice_engine.delete_reference`를 호출하지 않는다. 유저가 페르소나를 삭제해도
마스터 wav/json이 GCS에 남는다. 정리되는 경로는 회원 탈퇴(`routers/users.py:56`)뿐이다.

이 설계로 가면 유저가 레퍼런스를 소유하지 않게 되어 문제가 소멸하지만,
**마이그레이션 전까지는 기존 고아 파일이 계속 쌓인다.** 별도 건으로 처리한다.

## 음성 호출(핫워드) 조사 결과

원래 목표는 "삼성 사이드키처럼 버튼 길게 눌러 마이크 띄우기"였다. 조사 결과 **v1에서는
포기**하고 위젯·퀵설정 타일로 대체한다. 근거를 기록해 재논의 비용을 줄인다.

### 사이드키는 삼성이 잠가둔 자리다

One UI에서 사이드 버튼 길게 누르기에 배정 가능한 것은 "빅스비 호출" 또는 "전원 끄기
메뉴"뿐이며 서드파티는 후보로 뜨지 않는다. 서드파티 어시스턴트가 들어갈 수 있는 자리는
홈 제스처 / 홈 버튼 길게다.

### DSP 핫워드는 서드파티에 닫혀 있다

`VoiceInteractionService#createAlwaysOnHotwordDetector()`에 임의 문자열을 넘길 수는
있으나, `onAvailabilityChanged()`가 기기 지원 여부를 답한다. 우리 키프레이즈는
`STATE_HARDWARE_UNSUPPORTED`를 받는다.

등록(enrollment) 경로도 막혀 있다. AOSP `KeyphraseEnrollmentInfo`는
`com.android.intent.action.MANAGE_VOICE_KEYPHRASES` 인텐트를 가진 앱의
`android.voice_enrollment` XML만 스캔하며, 그 앱을 다음과 같이 검증한다:

```java
(ai.privateFlags & ApplicationInfo.PRIVATE_FLAG_PRIVILEGED) == 0   → 거부
!Manifest.permission.MANAGE_VOICE_KEYPHRASES.equals(ai.permission) → 거부
```

주석에도 "enrollment application needs to be a privileged system app"으로 명시되어
있다. `/system/priv-app` 선탑재가 조건이므로 Play 배포 앱은 구조적으로 불가능하다.

AAOS 문서가 관대하게 읽히는 이유는 자동차에서는 음성 앱을 OEM이 직접 선탑재하기
때문이다 — 앱 개발자와 등록 앱 소유자가 같은 주체다.

### 소프트웨어 핫워드의 청구서

DSP를 못 쓰면 CPU에서 모델을 돌려야 한다(Porcupine·openWakeWord 등). 공식 경로인
`HotwordDetectionService`(격리 샌드박스)도 **기본 어시스턴트 등록이 조건**이고,
안드로이드 12부터 마이크 사용은 호출한 어시스턴트 패키지로 귀속 표시되며 초록
인디케이터를 끄는 설정은 존재하지 않는다.

즉 상시 음성 호출의 대가는 — 구글 어시스턴트 포기 + 상시 CPU 배터리 + 상태바 초록 점
상시 노출 + Play 민감권한 심사.

### v1 결론

- **위젯 + 퀵설정 타일**로 탭 한 번에 마이크를 연다. 잠금화면에서도 동작하고,
  배터리 0 · 초록 점 없음 · 어시스턴트 슬롯 유지.
- 어시스턴트 등록과 핫워드는 **설정에 숨긴 옵트인으로 v2**. 앱을 오래 쓴 유저가
  대가를 알고 켜는 것이라 불만이 나오지 않는다.
- 호출어를 도입한다면 **"온리유야"로 고정**한다. 임의 이름은 단어당 모델 학습이
  필요해 즉석 생성이 불가능하다. 페르소나 이름은 자유로 두고 대화·알람 음성 안에서
  그 이름으로 불리게 한다(아마존과 같은 방식). 호출 시 응답을 페르소나 이름으로
  받아 인지 부조화를 완화한다.
- 검토했다가 접은 안: **충전 중 거치 모드에서만 핫워드 대기.** 배터리·프라이버시
  문제는 풀리지만, 충전 시간대는 대부분 자는 시간이라 대화 수요와 겹치지 않는다.

## v1 범위 밖

## 향후 확장 가능성: 크리에이터 보이스 파트너십

**확정된 계획이 아니다.** 검토 단계의 시나리오이며, 지금 결정에 영향을 주는 부분만
본문에 표시해두었다(위 두 인용 블록).

시나리오는 버튜버 등 크리에이터가 **본인 목소리를 제공**하고, 우리가 그것을 공식
보이스로 카탈로그에 올리는 것이다.

### 지금 설계가 이미 이것을 지원한다

이는 **UGC가 아니라 라이선스 콘텐츠**다. 유저가 남의 목소리를 올리는 것과 정반대다.

- 목소리 주인이 본인 동의로 제공 → 음성권 문제가 계약으로 해결
- 공급자가 소수이고 신원 확인됨 → 검열이 아니라 파트너 관리
- 우리가 검수하고 계약 → 프리셋 카탈로그에 항목이 추가되는 것뿐

유저 업로드 경로(`save_reference`)는 그대로 닫아두고 **파트너 채널을 별도 문으로**
연다. `voices` 테이블에 행을 추가하고 출처 메타데이터를 붙이면 되며, 아키텍처 변경이
사실상 없다.

이는 프리셋 결정이 옳았던 또 하나의 근거이기도 하다. 자유 생성 구조였다면 파트너
목소리가 유저 생성물 사이에 섞여 브랜드 관리가 불가능했을 것이고, "내 목소리가 어디
붙어 있는지 우리도 모른다"는 서비스에 크리에이터가 목소리를 줄 이유가 없다.

### 이 노선이 지금 결정에 미치는 영향

| 항목 | 변화 |
|---|---|
| 목소리 조합 | 파트너 세트는 **하드 락**(페르소나+목소리 묶음 고정) |
| 19금 | **재검토 여지 소멸.** 두 노선은 상호배타적 |
| 대중 노선과의 관계 | 충돌하지 않음 — 카테고리 분리로 처리, 스토어 노출 제외 |

19금이 닫히는 것은 손실만은 아니다. "19금은 하지 않는다"가 **제품 구조 자체로**
보장되면 파트너 입장에서 가장 큰 불안(내 목소리가 어디까지 쓰일지 모른다)이 계약서가
아니라 아키텍처로 제거되어 협상 카드가 된다. 또한 19금으로 얻을 수익과 파트너십
수익은 **양립 불가능한 선택지**이므로, 포기가 아니라 교환이다.

획득 채널로서도 강하다. 크리에이터 한 명이 들어오면 그 팬덤이 유입되고, 그 유저층은
대중 유저와 겹치지 않아 서로 간섭하지 않는다.

### 도입 시 설계해야 할 것

가장 어려운 것은 **계약 종료 처리**다. 유저가 오래 쓴 목소리가 만료로 사라지면 상실감이
크고, 유료 결제가 얽히면 환불 문제가 된다. 선택지는 기존 사용자 한정 유지(계약에 명시),
유예 기간 후 대체 안내, 또는 애초에 기간제 상품으로 명시하는 것이다. **계약서와 제품이
함께 설계되어야 한다.**

그 외:
- 사용 범위 명시 (알람·채팅 한정인지, 어떤 페르소나와만 결합되는지)
- 본인 동의 증빙 보관 — 딥페이크 규제 흐름상 필수
- 품질 책임 주체 — 파트너가 품질을 문제 삼으면 대응은 우리 몫
- 스토리지 10개 고정이 깨진다. 다만 파트너 수는 우리가 통제하므로 관리 가능

## 구현 단위 분할

이 문서는 방향을 정하는 스펙이고 하나의 구현 계획으로 다루기에는 크다.
실제 작업은 아래 단위로 쪼개 각각 계획을 세운다. 순서에도 의미가 있다 —
1이 2의 전제이고, 3은 독립이다.

1. **프롬프트 프리셋 전환** — 프리셋 상수 정의, `/chat` · `/alarm_script` 서버 조립,
   `PUT /personas` 입력 축소, `PersonaEditScreen` 자유 입력·슬라이더 제거
2. **목소리 분리 및 프리셋화** — `voices` 테이블, 레퍼런스 키 전환, `GET /voices`,
   `save_reference` 제거, 태그 기반 소프트 유도 UI
3. **위젯 · 퀵설정 타일** — 음성 진입점. 위 둘과 독립적으로 진행 가능
4. **마이그레이션** — 기존 유저 생성 페르소나 처리, 고아 레퍼런스 정리
