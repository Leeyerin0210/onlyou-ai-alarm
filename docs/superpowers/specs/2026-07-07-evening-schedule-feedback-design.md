# 저녁 일정 피드백 선톡 설계

날짜: 2026-07-07
상태: 승인됨

## 배경

- 채팅에서 추출된 일정이 Room/Firestore에 쌓이지만, 일정이 지나간 뒤 페르소나가 그것을 되짚어주는 장치가 없다.
- "일정 → 피드백 대화 → 답변이 RAG 기억으로 저장 → 다음 대화에서 자연스럽게 언급"되는 유대감 루프를 만드는 것이 목표.
- 일정별 즉시 팔로업(종료 시각 예측 + 개별 예약) 방식과 비교 검토한 결과, **저녁에 하루 일정을 묶어 한 번 묻는 방식**으로 확정:
  - "하루 최대 1건" 스팸 정책하에서는 일정별 방식도 어차피 하루 하나만 발송된다.
  - 종료 시각 필드 추가(DB 마이그레이션, 추출 프롬프트 수정), 일정별 예약/취소 로직이 전부 불필요해진다.
  - 종일 일정·며칠짜리 일정·시간 미상 일정의 발송 시각 문제가 자연 해소된다.
- 일정별 즉시 팔로업은 v2 후보로 남긴다.

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 방식 | 매일 저녁 1회, 오늘 일정을 묶어 페르소나가 안부를 묻는 선톡 |
| 발송 시각 | 기본 21:00, **설정 화면에서 변경 가능** |
| 오프라인 | 스킵 (재시도 없음) |
| 오늘 일정 없음 | 스킵 (잡담 선톡은 범위 외) |
| 반복 루틴 일정 | 목록에 포함하되 "반복 루틴" 표시를 붙여 프롬프트로 언급 빈도 제어 |
| 새벽 발송 | 발송 시각이 고정이므로 자연 충족. 워커 실행이 밀린 경우 예정 시각 +2시간 초과 시 스킵 |

## 설계

### A. 스케줄링 (Android)

- **WorkManager 주기 작업 방식** 사용: `PeriodicWorkRequest`(24시간) + `initialDelay`(다음 발송 시각까지), 고유 이름 `evening_feedback`.
  - 분 단위 정시성이 필요 없으므로 AlarmManager(정확 알람 권한)를 쓰지 않는다.
  - 워커 내부 자기 재예약은 금지: 실행 중인 고유 작업과 같은 이름으로 재등록하면 자기 자신이 취소되는 WorkManager 함정이 있어, 계획 단계에서 OneTimeWork 자기 재예약 대신 주기 작업으로 변경했다.
  - 재등록 트리거/정책: 앱 시작 시(`MiyaApplication`)는 `CANCEL_AND_REENQUEUE`, 설정에서 발송 시각 변경 시에도 `CANCEL_AND_REENQUEUE`, 부팅 시(기존 BOOT receiver가 있다면 함께).
    - 앱 시작에도 KEEP이 아닌 CANCEL_AND_REENQUEUE를 쓰는 이유: 주기 작업이 직전 실행 시점 기준으로 앵커되어, 윈도우 밖 실행 1회가 스케줄을 영구히 어긋나게 하는 드리프트를 방지하기 위함.
- 발송 시각은 SharedPreferences에 저장 (`ThemeRepositoryImpl` 패턴을 따르는 Settings 저장소).

### B. 워커 로직 (`EveningFeedbackWorker`)

실행 시 아래 순서로 체크, 하나라도 걸리면 **스킵 후 다음날 재예약** (재시도 없음):

1. 현재 시각이 예정 발송 시각 +2시간 초과 → 스킵 (밀린 작업이 새벽에 도는 것 방지)
2. 네트워크 오프라인 → 스킵
3. 오늘 일정 조회 결과 없음 → 스킵
   - "오늘 일정" 판정: `isDeleted == false` 이면서 (`date == 오늘`) or (`date <= 오늘 <= endDate`) or (`repeatDays`에 오늘 요일 포함)

통과 시:

4. 현재 선택된 페르소나의 systemPrompt + 최근 채팅 히스토리(일반 채팅과 동일한 히스토리 윈도우 재사용)로 chat API 호출.
   - message에 지시문: 오늘 일정 목록(제목/시간/장소, 반복 루틴은 `[반복 루틴]` 표시)과 함께 "이 일정들이 있던 하루가 끝났다. 페르소나로서 자연스럽게 하루가 어땠는지 물어봐라. 반복 루틴은 특별한 맥락이 없으면 굳이 언급하지 마라" 류의 지시.
   - 히스토리가 함께 가므로 어제 보낸 선톡과 표현이 겹치지 않게 LLM이 스스로 조절할 수 있다.
5. 응답 텍스트를 `ChatMessageEntity(sender = "AI")`로 chat_messages에 삽입. **지시문 자체는 USER 메시지로 남기지 않는다.**
6. 로컬 푸시 알림 표시 (제목: 페르소나 이름, 본문: 생성된 메시지 앞부분). 탭 시 채팅 화면으로 딥링크.

### C. 백엔드 (`chat.py`)

- `ChatRequestDto`에 `skip_side_effects: bool = false` 플래그 추가.
- 플래그가 true면:
  - `request.message` 기반 RAG 기억 자동 저장을 건너뛴다 (지시문이 기억을 오염시키는 것 방지).
  - 백그라운드 일정 추출도 건너뛴다 (지시문 속 일정 목록이 재추출되는 것 방지).
- 응답 스트리밍 등 나머지 동작은 동일 — 기존 chat 엔드포인트 재사용, 신규 엔드포인트 없음.

### D. 설정 UI

- 설정 화면(SettingsScreen)에 항목 추가:
  - 기능 on/off 토글 (기본 on)
  - 발송 시각 선택 (TimePicker, 기본 21:00)
- 시각 변경 또는 토글 on 시 워커 재예약, 토글 off 시 `evening_feedback` 작업 취소.

### E. 이후 대화 연결

- 유저가 선톡에 답하면 기존 채팅 파이프라인을 그대로 탄다 (이번 설계에서 추가 작업 없음).
  - 답변이 RAG 기억으로 저장되고, 선톡 AI 메시지도 히스토리에 있으므로 문맥이 자연스럽게 이어진다.

## 테스트

- 유닛: "오늘 일정" 판정 로직 (날짜 범위, 반복 요일, tombstone 제외), 다음 발송 시각 계산 (당일 발송 시각 전/후, 시각 변경 시).
- 유닛: 스킵 조건 (지연 초과, 일정 없음).
- 수동: 오프라인 스킵, 알림 탭 → 채팅 딥링크, 선톡 문구 품질, 반복 루틴 언급 억제.

## 하지 않는 것

- FCM / 서버 크론 (로컬 예약으로 충분).
- 일정별 즉시 팔로업, `durationMinutes` 필드 (v2 후보).
- 오프라인 재시도.
- 일정이 없는 날의 잡담 선톡.
- 일정 편집 다이얼로그 변경.
